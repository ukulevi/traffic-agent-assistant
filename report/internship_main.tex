\chapter*{Executive Summary}
\addcontentsline{toc}{chapter}{Executive Summary}

This report presents SmartTraffic What-If (STWI), an AI-agent application developed within the approved internship scope of AI-agent integration and governed data-platform development. STWI supports traffic operators in evaluating hypothetical incidents without automatically controlling field devices. It combines aggregate traffic data, a 30-minute GCN--LSTM baseline forecast, an offline-SUMO-trained surrogate ensemble, typed simulation queries, legal retrieval with structured citations, asynchronous jobs, and a fail-closed Counterfactual Safety Loop.

The product is deliberately positioned as decision support. It does not retain raw video, does not issue traffic-control commands, and requires human approval. Its machine-readable contract fixes the functional network at 20 nodes, the online tensors at \texttt{X[B,12,N,16]}, \texttt{M[B,12,N,16]}, and \texttt{A[N,N]}, and the forecast output at \texttt{Y[B,6,N,2]}. These constraints make the system testable and provide the data-governance and auditability needed for an AI-agent application.

The internship strengthened practical skills in requirements analysis, typed API design, AI-agent orchestration, data provenance, uncertainty handling, safety engineering, testing, technical documentation, and continuous integration. The resulting repository contains the implementation, contract tests, documentation, a technical report, presentation materials, and an operator-facing demonstration dashboard.

\chapter{Technical Product}

\section{Problem definition}

Traffic operators need to compare the likely effects of incidents such as accidents, floods, lane closures, demand surges, and signal changes. A useful tool must provide a baseline, estimate scenario impact, expose uncertainty, cite applicable legal or procedural evidence, and clearly distinguish a candidate from an approved operational action. STWI addresses this need as a human-in-the-loop what-if analysis system.

\section{System architecture}

STWI is organised into four tiers:

\begin{enumerate}[leftmargin=1.2cm]
  \item \textbf{Data tier:} aggregate camera and sensor evidence is converted into five-minute features without retaining raw video.
  \item \textbf{Forecast and simulation tier:} a GCN--LSTM produces the no-intervention baseline, while a separate surrogate ensemble estimates incident effects using offline SUMO training data.
  \item \textbf{Knowledge tier:} Qdrant and BGE-m3 support legal/SOP retrieval, structured citations, and typed simulation queries.
  \item \textbf{Agent and safety tier:} LangGraph coordinates bounded tools, Celery and Redis manage asynchronous work, FastAPI and SSE expose progress, and the Counterfactual Safety Loop applies fail-closed checks.
\end{enumerate}

\section{Data and API contracts}

The online model input is \texttt{X[B,12,N,16]} with a missing mask of the same shape and adjacency matrix \texttt{A[N,N]}. The baseline output is \texttt{Y[B,6,N,2]}, representing traffic volume and average speed for six five-minute forecast steps. Feature order, units, normalisation rules, topology version, model version, and data version are controlled centrally.

The job API accepts a typed incident and returns HTTP 202. Jobs move only through \texttt{queued}, \texttt{running}, \texttt{succeeded}, \texttt{needs\_review}, \texttt{failed}, or \texttt{expired}. Only \texttt{succeeded} can contain \nolinkurl{recommended_action}; \texttt{needs\_review} can contain only a non-executable \nolinkurl{candidate_action}.

\section{Safety, privacy, and legal grounding}

The system is fail-closed. High uncertainty, OOD inputs, invalid topology, missing valid legal evidence, authorisation errors, and timeouts prevent an executable recommendation. The Counterfactual Safety Loop is bounded to three iterations and always requires operator approval. The default V/C threshold of 0.9 is documented as configurable project policy, not law. Camera detections are used only as evidence for aggregate features; raw video is neither retained nor released.

\section{Operator experience}

The dashboard presents job state, timestamps, trace identifiers, model and data versions, incident context, network impact, uncertainty/OOD indicators, citations, candidate routes, and the reason for any fail-closed result. Visual prominence is given to review-required, failed, expired, high-uncertainty, and missing-evidence states. The interface does not imply automatic traffic control.

  \item a LaTeX technical report and presentation materials; and
  \item CI workflows for documentation validation, contract tests, JavaScript checks, and PDF compilation.

\section{Verification approach}

Verification is evidence-based. Contract tests check invariants such as tensor shapes, feature order, API statuses, performance targets, safety policy, and the mandatory legal corpus. Documentation validation detects contract drift and prohibited legacy architecture. Runtime and frontend tests exercise typed validation, orchestration, dashboard state, and demonstration behaviour. PDF and JavaScript build checks ensure that presentation artifacts remain usable.

No field-deployment or production-accuracy claim is made. Synthetic traffic producers do not represent one thousand decoded video streams, and the simulation-first demonstration does not claim real sensor observations or field calibration.

\chapter{Personal Reflection}

The internship provided an opportunity to apply computer-science foundations to a complex interdisciplinary problem involving AI, software architecture, transport operations, privacy, and legal constraints. Working within a professional data-solutions environment encouraged a disciplined approach: requirements had to be explicit, technical claims had to be testable, and every automated output had to remain reviewable by a responsible human operator.

The most valuable lesson was that an AI-agent product is not defined only by its model. Reliable behaviour depends on contracts, validation boundaries, provenance, calibrated uncertainty, operational user experience, and clear escalation paths. The guidance from the enterprise and Faculty supervisors helped turn these principles into concrete engineering decisions.

The internship programme also clarified the value of working in a professional data-solutions environment. Reviewing the product against the approved programme made the connection between technical delivery, documentation quality, confidentiality, and responsible human oversight concrete. This experience strengthened my appreciation for iterative review and for presenting a system in a form that both an enterprise supervisor and an academic reviewer can assess.

\chapter{Limitations and Future Work}

STWI remains a 13-week MVP and has not been deployed as a production traffic-control system. Its functional graph contains 20 nodes; the camera path is limited to recorded or RTSP demonstrations; the surrogate is reliable only within its calibrated scenario space; and legal retrieval cannot replace a qualified legal reviewer. The system never applies a field action automatically.

Future work should include a governed pilot with authorised aggregate field data, broader calibrated SUMO coverage, transfer evaluation across network topologies, high-availability infrastructure, stronger model and corpus governance, accessibility testing with operators, and independent safety and legal review before any field integration.
